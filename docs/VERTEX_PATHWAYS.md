# Vertex pathways and Star Key integration

**The Star is the VTA values you choose to share, and their encodings.** Its proposed role is a visual substrate for TSP exchanges. Design direction, not an implemented credential profile.

Star Key is intended to become a reusable attachment surface between VTA identity, MyTerms agreements, knowledge pathways and promise-graph artefacts. A vertex locates a selected reading; it does not establish the truth or authority of that reading.

## Sources already present

Soulbis Star carries per-vertex descriptions and City Key records. Soulbis Sigil derives a visual reading from canonical key content and can embed the complete key in a PNG. Skye compares touched vertices and lineage. The agentprivacy-mcp journey module preserves evidence in a private journey bundle and commits references into a City Key; folding an observation grants no authority. MyTerms owns the agreement-layer claims, with Swordsman agreement and Mage delegation responsibilities separate.

Reuse those carrier and canonicalization contracts before introducing another hash or sigil encoding. Do not label a shortened hash as the existing Soulbis sigil or use an opaque document hash as a Trust Task framework taskDigest.

## Proposed vertex attachment

An explicitly selected binding should reference: versioned vertex namespace and index; knowledge pathway and source versions; exact artefact content digest and canonicalization profile; promise-graph record and digest; agreement reference, version and scope; optional signed-statement reference and its separate verification status; and, for runnable work, a pinned recipe, inputs, environment, expected-result checks and requested capabilities. These are proposed fields, not a new canonical City Key schema.

Never include VTA tokens or signing secrets. Hash only the approved public projection or an explicitly authorized commitment. Public digests can expose equality and permit guessing; they do not supply confidentiality. Hashing a signed envelope identifies bytes, whereas verifying it requires the relevant DID method, key state, issuer, audience, freshness and revocation policy.

## Three distinct operations

1. Sigil: compact visual expression of a selected, versioned record, using the established Soulbis derivation. A portable picture may still contain its full payload.
2. Content commitment: deterministic identification of an exact approved representation. It does not attest authorship, agreement acceptance or execution success.
3. Proof: a later, specified statement with an actual verifier. Keep the proof control unavailable until that implementation exists.

## Overlap and execution

Shared coordinates suggest a comparison, not equivalent knowledge. Compare source and artefact identity, lineage and agreement scope before describing convergence. Different vertex namespaces need an explicit mapping.

A traced knowledge graph and promise graph support reproducibility. Deterministic execution additionally requires pinned inputs, code, dependencies, environment and controlled effects. Uncontrolled model calls and external services remain non-deterministic. Resolve the named recipe, present its permissions, verify prerequisites, execute in a bounded runner, check the result and record a separate receipt. Importing a key must never trigger execution.

## Next implementation layers

- Reuse the exact Soulbis sigil derivation with compatibility fixtures and explicit export-payload inspection.
- Introduce optional vertex bindings through the existing City Key/journey source owners; add allowlisted preview and opt-in export.
- Compare two approved projections by evidence references as well as touched vertices.
- Resolve MyTerms and signed-statement references with scoped disclosure and honest verification states.
- Add one pinned replay recipe and receipt after its permissions and determinism are demonstrated.

Current Star reader intentionally exports only name, palette and optionally claimed vertices. No vertex agreement binding, signature verification, runtime execution or proof generation is implemented in it yet.

## Storage and programmatic geometry

The Star can be the organizing carrier of a record, not merely its cover image. Distinguish an embedded approved payload, a content commitment, a resolvable reference and a private vault object. A hash is not storage and a reference is not a guarantee of availability. Each attachment needs its disclosure mode and availability status; retain private runtime material outside the shareable carrier unless explicitly selected.

A proposed geometry envelope should identify its mode (`derived`, `custom`, or `derived-with-overrides`), coordinate namespace, mapping ID/version, approved input digest, deterministic parameters and any explicit overrides. A reader must refuse unsupported mappings and malformed coordinates rather than silently presenting a default as a computed result. Derived readings must reset all ambient view state and reproduce against golden fixtures. Custom geometry remains a legitimate expression, but is not evidence of an outcome.

Keep display choices (camera, palette and animation) separate from measured geometry, and keep both separate from authority. A changed mapping can change a shape without changing the underlying evidence. Preserve both versions and the transformation provenance; do not overwrite the source record with its picture. Programmatic interpretation must name the statement being read, the mapping and the evidence status. No universal trust score follows from a shape.

This extends the next-layer design; the current reader still shows editorial artwork and has no geometry derivation engine.

## VRC-aware first contact

An applicable VRC can support a proposed introduction and disclosure policy. Verify its accepted profile, issuer, subject, audience, status and scope; show any proposed agreement change for approval before sharing. Only the approved projection changes the displayed Star. Page load and credential possession alone cannot amend terms, grant access or execute a recipe.

## Proof-carrying Star presentations

Next-stage proposal: a presentation carries an explicitly selected perspective, a versioned geometry reading and credential evidence or proofs of named claims. Bind the approved projection and mapping digest to the proof statement when relying on the visual reading. Specify issuer/profile acceptance, holder binding, credential status, audience, purpose, fresh challenge and expiry. Verify before granting the named action. Assignment identifies a recipient/subject/scope; it does not transfer a credential by copying its image.

Start with one claim and one verifier. Selective disclosure, aggregation and succinct proofs are separate choices, and proof size is not guaranteed to be smaller. No arbitrary credential-to-proof conversion exists in this pilot. Test wrong recipient, replay, expired/revoked credentials, altered geometry/projection and unsupported proof profiles before accepting such an exchange.
